# 雅思口语特训场景方案调研与设计

## 背景

UniSpeaking 当前的场景训练主要采用“学词语 → 读句子 → 场景模拟”的训练流程。

雅思口语考试具有独立的考试结构，包含 Part 1、Part 2 和 Part 3。用户进入雅思口语特训后，更适合直接进入考官提问和用户回答的模拟考试流程，因此不能完全复用现有普通场景训练方式。

今天计划围绕雅思口语特训的产品形态和技术实现方向进行调研与方案设计。

## 今日计划

今天主要思考并明确以下问题：

### 1. 雅思口语训练流程

研究雅思口语 Part 1、Part 2、Part 3 的不同形式，以及这些形式应该如何在 UniSpeaking 中进行产品化呈现。

重点思考：

- 是否需要完整模拟雅思口语考试流程。
- 三个 Part 应该如何切换。
- 每个 Part 应该包含多少问题。
- Part 2 的准备时间和回答时间如何体现。
- 训练过程中是否允许暂停、重试或跳过。
- 模拟考试模式与普通练习模式是否需要区分。

### 2. 题库组织方式

研究三个 Part 的题库应该如何组织和管理。

重点对比：

- 将题库保存为本地 JSON 文件。
- 将题库存入 Supabase 数据库。
- 是否需要使用 RAG 或向量检索。
- Part 2 与 Part 3 是否需要建立主题关联。
- 抽题单位应该是单个问题、题组还是完整题卡。
- 如何避免用户在短时间内重复抽到相同题目。
- 后续题目更新、上下架和版本管理如何处理。

### 3. 抽题与组卷逻辑

设计一次雅思口语特训应该如何生成完整试题。

重点思考：

- 是否分别从三个题库中随机抽题。
- Part 3 是否应该根据 Part 2 的主题进行匹配。
- 是否需要根据用户水平调整题目难度。
- 是否需要保存本次考试的题目快照。
- 是否需要支持固定试卷与随机试卷两种模式。
- 如何保证每次考试的题目组合稳定、可追踪和可复现。

### 4. 考试流程控制方式

研究整个雅思口语考试流程应该由什么模块控制。

重点对比：

- 完全通过 Prompt 让大模型控制流程。
- 通过前端状态控制流程。
- 通过后端状态机控制流程。
- 前端、后端和 Realtime 模型之间如何分工。

需要重点确认：

- 当前处于哪个 Part。
- 当前正在回答哪道题。
- 什么时候进入下一题。
- 什么时候允许 AI 追问。
- 什么时候结束当前 Part。
- 什么时候结束整场考试。

### 5. Realtime 模块复用方式

分析现有自由对话 Realtime 能力中，哪些部分可以直接复用，哪些部分需要为雅思场景单独设计。

计划重点检查：

- 麦克风采集是否可以直接复用。
- RealtimeClient 是否可以直接复用。
- 字幕和音频播放是否可以复用。
- 当前 Clara 自由对话 Prompt 是否需要替换为雅思考官 Prompt。
- 如何避免模型在考试过程中进行教学、纠错或偏离题目。
- 是否需要为雅思场景增加独立的 Session Hook 和状态管理模块。

### 6. 回答记录与结果数据

研究考试过程中需要保存哪些数据，为后续评分和学习报告做准备。

计划考虑：

- 每道题的题目内容。
- 用户回答转写。
- 回答开始和结束时间。
- 回答持续时长。
- 当前 Part。
- 是否存在追问。
- Part 2 的准备和回答时间。
- 完整考试状态。
- 用户是否中途退出。
- 本次考试使用的题库版本。

### 7. 评分与复盘方向

初步研究雅思口语训练结束后的反馈形式，但今天暂不直接实现完整评分系统。

重点思考：

- 是否按照雅思口语四个评分维度生成反馈。
- 文本转写可以支持哪些基础评价。
- 发音和流利度是否需要额外的音频分析能力。
- AI 评分应该如何避免表现得过于绝对。
- 是否需要生成分 Part 的问题分析。
- 是否需要根据用户薄弱项推荐后续练习内容。
- RAG 是否更适合用于考后反馈和学习资料推荐，而不是核心抽题。

## 最终方案摘要

> 方案状态：2026-07-20 已完成产品与技术方向收敛。  
> 本期范围：只设计本地开发阶段的产品流程和软件边界，不讨论部署、上线、Supabase 生产配置、RLS 或运维。

雅思口语特训不应直接复制现有“学词语 → 读句子 → 场景模拟”流程，而应建立独立的 `IELTS ExamSession`。推荐方案是：

- 用同一套考试会话内核支持 Part 1、Part 2、Part 3 专项练习和完整模考。
- 题库由开发人员维护后端 JSON，MVP 不使用数据库或 RAG 抽题。
- 组卷器在开考前随机生成整张试卷快照，开考后不再换题。
- 后端 `ExamStateMachine` 是 Part、题号、阶段、时限和允许操作的唯一权威。
- Realtime 模型作为语音考官，负责发问、必要过渡和受限追问，不决定考试流程。
- Part 2 始终展示完整题卡；60 秒准备时可记笔记，正式回答后笔记锁定为只读。
- 完整模考不允许暂停、跳题或重试；专项练习允许重试和进入下一题。
- 考后按 IELTS 四个维度生成带证据的 AI 练习反馈，不输出精确 0–9 分，不宣称是官方成绩。

## 一、不可破坏的考试规则

产品流程以 IELTS 官方公开格式为边界：

| 阶段 | 官方形式约束 | UniSpeaking 产品化规则 |
| --- | --- | --- |
| 全程 | 共 3 个 Part，总时长约 11–14 分钟 | 完整模考按 Part 1 → Part 2 → Part 3 单向推进 |
| Part 1 | 约 4–5 分钟，围绕熟悉话题进行问答 | 默认组 2 个题组，按时间预算执行 6–8 个核心问题 |
| Part 2 | 1 分钟准备，1–2 分钟长回答，通常再有 1–2 个同题收尾问题 | 完整题卡持续可见；准备阶段可记笔记；回答阶段锁定笔记 |
| Part 3 | 约 4–5 分钟，与 Part 2 话题相关且更抽象、深入 | 只能从与 Part 2 `topic_cluster` 相同的 Part 3 题组中选择 |

上表的 6–8 题、2 个题组等数字是 UniSpeaking 的默认产品配置，不对外声称为 IELTS 永久固定题数。官方约束以考试形式和时长为主，题量必须保持可配置。

参考资料：

- [IELTS Speaking test format](https://ielts.org/take-a-test/test-types/ielts-academic-test/ielts-academic-format-speaking)
- [IELTS Speaking sample tasks](https://ielts.org/cdn/ielts-sample-tests/ielts-speaking-sample-tasks-2023.pdf)
- [IELTS Speaking band descriptors](https://ielts.org/cdn/ielts-guides/ielts-speaking-band-descriptors.pdf)

## 二、候选技术路线与选择

### 路线 A：完全由 Prompt 控制

让 Realtime 模型记住全部题目、时长和转场规则，自行决定何时换题、换 Part 和结束。优点是代码少，但无法稳定保证题目顺序、计时、题量、可复现性和异常恢复，不适合考试型产品。

### 路线 B：确定性编排 + Realtime 考官（采用）

由后端负责题库、组卷、快照、状态机和时限，Realtime 模型只获得“当前允许说什么”的最小上下文。优点是考试可控、流程可测、数据可回放，同时仍保留语音考官的自然感。代价是需要增加一套独立的 IELTS 领域模块。

### 路线 C：RAG / 多模型工作流

用向量检索找题，由多个模型分别组卷、考试和评估。这条路线适合未来的大规模资料推荐或复杂学习报告，但对当前结构化小题库属于过度设计。MVP 不采用。

## 三、产品入口与模式区分

雅思口语特训首页提供四个入口：

1. Part 1 专项练习。
2. Part 2 专项练习。
3. Part 3 专项练习。
4. 完整模拟考试。

| 能力 | 专项练习 | 完整模考 |
| --- | --- | --- |
| 题目范围 | 用户选择 Part，可选基础/标准/进阶训练标签 | 不按用户水平降难度 |
| Part 1/3 题目文字 | 显示 | 不显示独立题卡，只语音提问 |
| Part 2 题卡 | 始终显示 | 始终显示 |
| 实时字幕 | 默认显示 | 默认隐藏，会话中可随时开启 |
| 暂停 | 只允许在题目之间暂停 | 不允许 |
| 重试当前题 | 允许 | 不允许 |
| 进入下一题 | 允许 | 由状态机控制，用户不能跳题 |
| 中途退出 | 保存已完成的训练记录 | 二次确认后标记 `abandoned`，不生成完整模考结论 |
| 过程教学反馈 | 可在一道题结束后给简短提示 | 全程不纠错、不教学，结束后统一反馈 |

“暂停”不得冻结 Part 2 已经开始的 60 秒准备或计时回答；专项练习也只能在进入下一题前暂停。

## 四、完整模考产品流程

### 4.1 开考前

1. 展示 11–14 分钟预计时长和不可暂停/跳题/重试规则。
2. 检查麦克风权限、输入音量和 Realtime 连接。检查未通过时不创建正式考试。
3. 提供“保存我的回答录音”开关，默认关闭；用户主动开启后才分段保存原始音频。
4. 字幕默认关闭，但开考后仍可通过字幕按钮随时开启或关闭。
5. 后端完成随机组卷和校验，写入不可变的 `paper_snapshot`。

### 4.2 Part 1

- 顶部只显示 `Part 1 of 3`、考试进度和麦克风状态，不显示题目卡。
- AI 考官先进行简短身份/流程引导，再按快照顺序提问。
- 默认两个熟悉话题组，时间预算 4–5 分钟。
- 每个核心问题最多允许 1 个当前话题内的动态追问，且只在剩余时间允许时发生。
- 完成最小覆盖题数后，状态机根据剩余时间判断是否开启下一题，不由模型自己结束 Part。

### 4.3 Part 2

Part 2 的状态顺序固定为：

```text
part2_intro
    ↓
part2_preparing (60s)
    ↓
part2_answering (1–2min, hard max 120s)
    ↓
part2_rounding_off (normal 1–2 questions from JSON)
    ↓
part3_intro
```

Part 2 页面采用已确认的“考试桌面·全宽题卡”布局：

- 顶部：Part/阶段、倒计时、字幕开关。
- 中部：完整 cue card，包含主题句、全部 `You should say` 要点和最后的 `and explain...` 要求。
- 底部：准备笔记、麦克风与当前回答状态。
- 60 秒准备时：题卡可见，笔记可编辑。
- 正式回答时：题卡和笔记继续可见，笔记立即锁定为只读。
- 回答到 120 秒时，考官按规则结束长回答；不因用户未覆盖某个提示点而自动延时。

### 4.4 Part 3

- 题组必须与 Part 2 具有相同 `topic_cluster`。
- 完整模考不显示独立题目卡，默认只听考官语音。
- 时间预算 4–5 分钟，默认执行 3–5 个核心问题或 JSON 中预设的 probe。
- 模型可对当前回答做最多 1 次自然追问，但不能切换主题、改写后续核心问题或超过时间预算。

### 4.5 结束与反馈

1. 后端将会话标记为 `completed`，冻结记录。
2. 前端先展示客观记录：完成的 Part、总用时、每题回答时长、转写、Part 2 笔记和录音回放（如已开启）。
3. 评估模块异步生成结构化 AI 练习反馈；评估失败不会丢失原始考试记录。
4. `abandoned` 或技术中断的完整模考可查看已经完成的记录，但不生成代表整场表现的总结。

## 五、题库组织方案

### 5.1 存储选择

MVP 使用后端 JSON，理由是题库当前由开发人员直接改文件、更新频率低，不需要多人后台、复杂查询或实时上下架。RAG 不适合核心抽题，因为题目是结构化、需要严格版本和可复现的数据。

建议目录：

```text
backend/ielts/
├── question_bank/
│   ├── manifest.json
│   ├── part1.json
│   ├── part2.json
│   └── part3.json
├── schemas/
│   └── question-bank.schema.json
└── repositories/
    └── question-bank-repository
```

JSON 文件只由后端读取，前端不直接加载或修改题库。业务代码只依赖 `QuestionBankRepository`，不在组卷器和状态机中散落文件路径。

### 5.2 `manifest.json`

```json
{
  "bank_version": "2026.07.20",
  "schema_version": 1,
  "locale": "en-GB",
  "files": {
    "part1": "part1.json",
    "part2": "part2.json",
    "part3": "part3.json"
  },
  "defaults": {
    "recent_completed_sessions_to_avoid": 5,
    "part1_target_seconds": 270,
    "part3_target_seconds": 270
  }
}
```

### 5.3 Part 1 题组

```json
{
  "group_id": "p1_home_001",
  "version": 1,
  "status": "active",
  "topic": "Home and accommodation",
  "training_level": "standard",
  "questions": [
    {
      "question_id": "p1_home_001_q1",
      "version": 1,
      "text": "What kind of accommodation do you live in?"
    }
  ]
}
```

Part 1 的抽题单位是“题组”，不是互不相干的单题。一场完整模考默认抽取两个不同熟悉话题组。

### 5.4 Part 2 完整题卡

```json
{
  "card_id": "p2_person_001",
  "version": 1,
  "status": "active",
  "topic_cluster": "people_and_relationships",
  "training_level": "standard",
  "topic_sentence": "Describe a person who has influenced you.",
  "you_should_say": [
    "who this person is",
    "how you know this person",
    "what this person did"
  ],
  "explain": "and explain how this person influenced you.",
  "rounding_off_questions": [
    {
      "question_id": "p2_person_001_r1",
      "version": 1,
      "text": "Do you still keep in touch with this person?"
    }
  ]
}
```

Part 2 的抽题单位必须是整张 cue card，不允许分别抽主题句和提示点后临时拼装。

### 5.5 Part 3 关联题组

```json
{
  "group_id": "p3_people_001",
  "version": 1,
  "status": "active",
  "topic_cluster": "people_and_relationships",
  "training_level": "standard",
  "questions": [
    {
      "question_id": "p3_people_001_q1",
      "version": 1,
      "text": "What kinds of people influence young people today?",
      "probes": [
        "Why do you think that is?",
        "Has this changed compared with the past?"
      ]
    }
  ]
}
```

Part 2 和 Part 3 通过稳定的 `topic_cluster` 关联。`topic_cluster` 由开发人员在编辑题库时明确填写，不让 AI 在考试现场进行语义猜测。

### 5.6 题库校验与版本

启动开发环境或运行题库检查脚本时，必须验证：

- ID 全局唯一，版本为正整数。
- Part 2 题卡包含主题句、至少 3 个 `you_should_say` 要点和 `explain`。
- 每个启用的 Part 2 `topic_cluster` 至少存在 1 个启用的 Part 3 题组。
- 启用题组具备满足最小组卷数量的问题。
- 未知字段、空文本、非法状态和重复关联直接报错，不带病开考。

开发者修改文字时同步提升题目 `version`；题库整体发生可见改动时提升 `bank_version`。历史考试快照保留当时的 `rendered_text`，因此不会被新 JSON 覆盖。

### 5.7 何时再迁移数据库

仅在出现以下信号后再评估数据库：

- 题库改为非开发人员维护。
- 需要频繁上下架、定时发布、多人并行编辑或审批。
- 需要跨版本查询、复杂运营筛选和大量统计。
- JSON 文件已大到代码审查和冲突合并成为稳定痛点。

## 六、随机组卷逻辑

MVP 只做随机组卷，不做人工固定试卷。但“随机”只存在于开考前，正式会话必须执行冻结快照。

### 6.1 组卷顺序

```text
1. 读取并校验题库版本
2. 读取用户最近 5 场已完成训练的题目 ID
3. 从 active Part 2 cue cards 中排除近期重复并随机抽取 1 张
4. 使用该 cue card.topic_cluster 筛选 Part 3 兼容题组
5. 抽取 Part 3 题组和按顺序排列的候选核心问题
6. 抽取 2 个不同的 Part 1 熟悉话题组
7. 验证当前试卷无重复、题数和关联均满足配置
8. 写入 paper_snapshot，然后才允许开考
```

### 6.2 重复回避

- 当前试卷内题目和题卡绝不重复，这是硬约束。
- 默认尽量避开用户最近 5 场已完成训练的题目，这是软约束。
- 候选池不足时，从最早一场开始逐步放宽历史回避，直到能够组卷。
- 不得放宽当前试卷唯一性、题目启用状态和 Part 2/3 主题关联。
- 快照记录实际的回避窗口和放宽级别，便于测试和排查重复题。

### 6.3 时间预算与题量

| Part | 时间预算 | 产品默认配置 | 推进原则 |
| --- | --- | --- | --- |
| Part 1 | 240–300 秒 | 2 题组，最小 6、目标 8、上限 8 个核心问题 | 先满足最小覆盖，剩余时间不足则不开新题 |
| Part 2 | 准备 60 秒，长回答最长 120 秒 | 1 张题卡，正常执行 1–2 个 JSON 收尾问题 | 结构固定，不因笔记或回答内容改变时限 |
| Part 3 | 240–300 秒 | 最小 3、目标 4、上限 5 个核心问题 | 优先完成主题深度，动态追问受全局剩余时间限制 |

时限到达时如果用户正在说话，允许最多 10 秒的话轮收尾宽限；超过宽限后由考官礼貌打断并进入下一阶段。该宽限是统一配置，不由模型自行决定。

### 6.4 试卷快照

快照至少保存：

- `paper_id`、`assembly_version`、`bank_version`和创建时间。
- 每道题的 `question_id + version + rendered_text`。
- Part 2 的完整 cue card 和 `topic_cluster`。
- 题目顺序、Part 时间预算、最小/目标/最大题数。
- 历史重复回避窗口与放宽级别。
- 随机种子可用于调试，但不能替代完整题目文本快照。

## 七、考试状态机

### 7.1 总体状态

```text
created
  → preflight
  → assembling
  → ready
  → part1_intro → part1_running
  → part2_intro → part2_preparing → part2_answering → part2_rounding_off
  → part3_intro → part3_running
  → completing → completed

Any running state
  → abandoned            (用户确认退出)
  → technical_interrupted (不可恢复的技术中断)
```

`part1_running` 和 `part3_running` 内部包含 `asking → listening → turn_finalizing → advancing`；Part 2 单独拆分准备、长回答和收尾，不能用普通题目状态代替。

### 7.2 权威与计时

- 后端保存 `state_entered_at`、`deadline_at`、当前 Part、当前题和允许操作。
- 前端倒计时是基于后端 `deadline_at` 的视觉投影，刷新页面或本地计时漂移不得延长考试。
- 所有状态变更均带 `expected_state_version`，重复事件不能让状态连跳两次。
- Realtime 模型说出“我们进入 Part 3”不代表实际已经进入；只有后端成功转移后，前端和模型才收到新状态。

### 7.3 允许操作

完整模考运行中只允许：

- 开启/关闭字幕。
- 申请退出，并在二次确认后退出整场。
- 修改本地音量等不影响考试内容的设备偏好。

专项练习额外允许：

- 重试当前题。
- 结束当前题并进入下一题。
- 在题目边界暂停或结束本次练习。

所有按钮显示均来自后端返回的 `allowed_actions`，前端不自行猜测当前能做什么。

## 八、Realtime 复用与新增边界

### 8.1 可直接复用

当前 `7.14/UniSpeaking_Complete_UI` 中可复用：

- 麦克风权限、音频采集和设备错误处理。
- `src/realtime/realtime-client.mjs` 的 WebRTC/DataChannel 连接与事件通道。
- AI 音频播放、用户输入转写和通用连接状态。
- 会话开始/结束 API 的基础形态。
- 已有的字幕渲染能力，但需受 IELTS `mode_policy` 开关控制。

### 8.2 不能直接复用

- 普通场景的“词语 → 句子 → 模拟 → 诊断”流程。
- Clara 自由对话 Prompt。
- 只有“连接/聆听/说话”的通用 Realtime state，它无法表达 Part、题号、准备和时限。
- 普通场景的过程教学反馈和通用诊断文案。

### 8.3 建议新增模块

```text
Frontend
├── IELTSRoute / IELTSHomeView
├── ExamView
├── Part2CueCardView
├── ExamSessionController
├── ExamStateStore
├── CaptionPreference
└── OptionalAnswerRecorder

Backend domain
├── QuestionBankRepository
├── JsonQuestionBankRepository
├── QuestionBankValidator
├── PaperAssembler
├── ExamStateMachine
├── ExamDialogueController
├── SessionRepository
└── FeedbackService
```

前端的 `ExamStateStore` 和通用 `RealtimeState` 必须分开：前者表示“考试进行到哪”，后者表示“语音链路正在做什么”。两者可同时是 `part2_answering + ai_speaking`，不能强行合并成一个状态枚举。

### 8.4 模型的权限

Realtime 考官可以：

- 用自然考官语气说出后端下发的当前核心问题。
- 说出状态机允许的开场、转场和结束话术。
- 在当前主题内提议一个自然追问，由 `ExamDialogueController` 根据次数、剩余时间和主题边界决定是否允许。

Realtime 考官不可以：

- 自己抽题、换题、生成新的核心问题或改写快照中问题的语义。
- 自己判定进入下一题、下一 Part 或结束考试。
- 在完整模考中教学、纠错、评分、安慰式延长时间或因用户要求跳过规则。

核心问题应作为明确的 `spoken_text` 下发，并对模型输出转写做契约检查。若发生实质性改写、自行跳题或违规教学，记录 `protocol_violation`，由控制器纠正或重播当前问题，但不推进考试状态。

## 九、核心数据记录

题库存储和考试记录存储是两个不同问题。题库已确认使用后端 JSON；考试记录则通过 `SessionRepository` 接口保存。本地 MVP 测试可使用内存适配器和本地 JSONL 适配器，不在本方案中锁定生产数据库。

### 9.1 ExamSession

- `session_id`、`user_id`、`mode`、`selected_part`。
- `status`: `created/ready/running/completed/abandoned/technical_interrupted`。
- `paper_snapshot_id`、`bank_version`、`state_version`。
- `started_at`、`completed_at`、`current_part`、`current_item_id`。
- `captions_default=false`、`captions_used`、字幕开关时间轨迹。
- `recording_enabled=false` 以及开考前的用户选择。
- `abandon_reason` 或 `technical_failure_code`。

### 9.2 AnswerRecord

- `answer_id`、`session_id`、`part`、`question_id`、`question_version`。
- `attempt_no`（专项重试时递增，完整模考始终为 1）。
- `is_follow_up`、`parent_question_id`、`follow_up_source=json/dynamic`。
- 实际说出的问题文本、用户最终转写和转写完整性标记。
- `asked_at`、`answer_started_at`、`answer_ended_at`、`duration_ms`、静音/中断等客观指标。
- `audio_ref`：只在用户开考前主动开启录音时存在。

### 9.3 Part 2 特有记录

- 60 秒准备的开始、结束和是否被技术中断。
- 准备笔记最终快照。
- 笔记锁定时间。
- 长回答实际时长、是否到达 120 秒上限、是否被考官打断。

### 9.4 状态事件

保存 `from_state`、`to_state`、`event`、`occurred_at`、`state_version`和触发原因。这份事件轨迹用于解释计时、异常中断和“为什么跳到下一 Part”，不能只保存最终状态。

## 十、考后 AI 练习反馈

### 10.1 报告结构

1. 本次练习概览：模式、Part、用时、题目覆盖、是否使用字幕和录音。
2. Fluency and Coherence：使用回答时长、停顿、中断和转写中的连贯证据。
3. Lexical Resource：使用转写中的具体表达作为证据。
4. Grammatical Range and Accuracy：引用具体句子说明表现和可改进点。
5. Pronunciation：只有存在可靠原始音频且后续已实现合格的音频分析时才评价；否则显示“证据不足，未评估”。
6. 分 Part 问题复盘：展示题目、回答、证据和一条最优先的改进建议。
7. 下一步训练建议：从已有专项练习中推荐 1–2 个具体动作，MVP 不用 RAG 生成资料。

### 10.2 文案边界

- 可使用：“AI 练习反馈”“参考 IELTS Speaking 评价维度”“本次表现证据”。
- 不可使用：“官方成绩”“官方标准打分报告”“与认证考官等价”。
- MVP 不输出精确 0–9 分，也不用小数点营造不存在的精确性。
- 现有会员页“官方标准打分报告”文案应在实施时改为“参考 IELTS 维度的 AI 练习报告”。

## 十一、异常与边界处理

| 异常 | 处理原则 |
| --- | --- |
| 题库 JSON 无法通过 schema | 开考前阻断，显示可定位到文件和 ID 的开发错误 |
| Part 2 无兼容 Part 3 题组 | 开考前换一张 Part 2 题卡重试组卷；不在考试中生成新题 |
| 题库不足以回避近 5 场 | 逐级放宽历史回避，快照中记录放宽级别 |
| 麦克风未授权/无输入 | 预检阶段阻断，不计为考试放弃 |
| 短暂网络抖动 | 允许最多 10 秒的自动重连宽限，界面显示技术恢复中；用户不获得主动暂停能力 |
| 超过宽限仍无法恢复 | 标记 `technical_interrupted`，保存已有记录，不生成完整模考结论，允许新建一场 |
| 模型自行换题/教学 | 记录 `protocol_violation`，后端不推进状态，重新下发当前正确话术 |
| 转写缺失 | 保留时间和完整性标记；反馈中降低结论范围，不伪造回答文本 |
| 考后评估失败 | 考试仍保持 `completed`，报告状态标记为 `failed/retryable`，不丢失原始记录 |

## 十二、MVP 范围

### 12.1 本期必须实现

- IELTS 独立入口、Part 1/2/3 专项练习和完整模考。
- 后端 JSON 题库、schema 校验和 `QuestionBankRepository`。
- Part 2/3 `topic_cluster` 关联。
- 随机组卷、近 5 场重复回避、完整试卷快照。
- 后端权威 `ExamStateMachine` 和前端倒计时投影。
- Part 2 全宽题卡、60 秒准备、可编辑笔记与回答期锁定。
- 完整模考与专项练习的操作权限区分。
- 字幕默认隐藏但可在会话中切换。
- 录音默认关闭，开考前由用户主动开启。
- 题目、转写、用时、笔记、状态事件和退出原因的结构化记录。
- 四维结构化 AI 练习反馈，缺少可靠证据的维度显式标记未评估。

### 12.2 本期明确不做

- 部署上线、生产数据库、RLS、运维、监控和计费。

- RAG 抽题、向量检索或让模型生成核心考题。
- 人工固定试卷、试卷编辑器和多人统一卷。
- 完整模考的暂停、跳题和重试。
- 根据用户水平动态改写完整模考题目。
- 精确 IELTS 0–9 估分或“官方标准报告”。
- 在没有可靠音频证据的情况下评价发音。

## 十三、验收与测试草案

### 13.1 题库契约

- 任何重复 ID、空题目、缺失 cue card 字段或孤立 `topic_cluster` 都必须在开考前报错。
- 开发者修改 JSON 后，旧会话快照仍能展示当时的题目文本。

### 13.2 组卷性质

- 连续生成大量试卷，每张当前试卷内无重复题目。
- 每张 Part 3 `topic_cluster` 都与 Part 2 一致。
- 候选池足够时不出现最近 5 场的题；候选池不足时按预定顺序放宽，不陷入死循环。
- 使用同一快照可完整回放题目顺序和配置。

### 13.3 状态机

- 非法跳转、重复事件和旧 `state_version` 事件被拒绝。
- 完整模考不出现暂停、跳题或重试操作。
- Part 2 准备严格按后端 deadline 结束，页面刷新不会重置 60 秒。
- 完整模考中途退出为 `abandoned`，不生成完整结论。

### 13.4 UI 与模式

- Part 2 准备和回答期间均展示完整题卡。
- Part 2 笔记在准备时可编辑，进入回答状态后立即只读。
- 完整模考 Part 1/3 不显示独立问题卡；专项练习显示。
- 完整模考字幕默认关闭，会话中开启后只影响展示，不影响考试状态。
- 录音未主动开启时不生成 `audio_ref`。

### 13.5 Realtime 契约与反馈

- 模型尝试跳 Part、跳题或教学时，后端权威状态不变。
- 动态追问不超过每个核心问题 1 次，并且不超过 Part 时间预算。
- 报告每条判断都能定位到转写、时间或音频证据；无证据时显式降级。
- 产品界面和报告中不出现“官方成绩”“官方标准打分报告”或精确 0–9 估分。

## 十四、开发优先级与后续演进

### 阶段 1：确定性考试骨架

先实现 JSON schema、Repository、PaperAssembler、paper snapshot 和纯状态机测试。这一阶段可不连真实 Realtime 模型，先证明组卷和流程不会失控。

### 阶段 2：Realtime 考官接入

复用现有麦克风、WebRTC/DataChannel、转写和音频播放，新增 `ExamDialogueController` 和 IELTS 考官 Prompt，完成 Part 1/2/3 主链路。

### 阶段 3：练习交互与记录

实现 Part 2 全宽题卡、笔记锁定、字幕开关、录音自愿开关、专项重试与结构化 AnswerRecord。

### 阶段 4：考后反馈

先产出有证据的文本/时间反馈，再根据原始音频保存率和分析稳定性评估是否加入发音分析。精确估分、RAG 学习资料和个性化长期计划继续留在后续版本。

## 十五、关键架构决策记录

| 决策 | 选择 | 放弃 | 原因 | 代价/后续触发信号 |
| --- | --- | --- | --- | --- |
| 题库存储 | 后端 JSON + Repository | 当前上数据库 | 开发人员低频改文件的最小方案 | 多人编辑、频繁发布、复杂查询时迁移 |
| 抽题 | 结构化随机组卷 | RAG/模型生成核心题 | 稳定、可版本化、可复现 | 需要维护题库 schema 和校验器 |
| Part 2/3 关联 | `topic_cluster` | 一对一固定套题、AI 临场匹配 | 兼顾组合多样性和可控性 | 编辑 Part 2 时必须同步确保 Part 3 覆盖 |
| 流程控制 | 后端状态机 | Prompt 全控、前端单独控制 | 计时和跳转可测、可审计 | 需要明确事件契约和幂等处理 |
| 试卷类型 | MVP 只随机快照 | 同期固定试卷 | 减少试卷编辑和发布复杂度 | 未来增加 `paper_template` 而不改状态机 |
| 完整模考难度 | 统一题库 | 按用户水平动态改题 | 保持模考可比性和题目语义稳定 | 专项练习用非官方训练标签补充 |
| 字幕 | 模考默认隐藏、会话中可开 | 强制隐藏或强制显示 | 在仿真度和用户辅助之间取得平衡 | 需在会话中记录是否使用过字幕 |
| 原始录音 | 默认关闭、开考前主动开启 | 无条件默认保存 | 保留回放/发音分析能力，同时尊重用户选择 | 未开启时发音维度不评估 |
| 评估 | 四维证据化练习反馈 | 精确 0–9 估分 | 避免虚假精确和官方误导 | 之后只有在专门 eval 证明可靠后才评估分数区间 |

## 结论

本方案的核心不是“换一个 IELTS Prompt”，而是在现有 Realtime 语音底座之上新建一个可测试的考试领域层。JSON 题库解决“考什么”，`PaperAssembler` 解决“这次考哪些”，`ExamStateMachine` 解决“现在进行到哪”，Realtime 考官解决“如何自然地说出来”，考后评估解决“如何用证据帮助用户改进”。这些责任不应重新混回一个 Prompt 中。
