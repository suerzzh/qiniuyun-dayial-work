## 一、开场先给结论

这一阶段，我完成的核心工作，是把 UniSpeaking 从一个“本地可以运行的 AI 英语口语 Demo”，改造成一套“通过正式域名可以稳定访问、能够建立真实语音会话、并且具备基本安全和验证机制的线上产品”。

最终，完整 React 产品前端部署在 Vercel；实时会话网关部署在原有 Supabase 项目的 Edge Function；浏览器通过 WebRTC 和阿里云百炼 Qwen Realtime 建立实时音频链路；Supabase 数据库保存会话元数据、最终字幕和质量指标，但不保存用户原始音频。

目前 `app.unispeaking.cn`、`www.unispeaking.cn` 和 `unispeaking.cn` 三个域名都指向同一套新版产品。自由对话页面能够完成麦克风授权、会话创建、SDP 交换、AI 音频播放、实时字幕、状态更新以及通话结束后的资源释放。

## 二、5—7 分钟现场逐字讲稿

### 0:00—0:40：我完成了什么

各位老师好，这一阶段我主要负责 UniSpeaking 自由对话能力的产品化和生产部署。

项目最初有两套代码：完整产品 UI 和能够实时语音对话的独立 Demo。我没有使用 iframe，也没有保留两个独立应用，而是以完整 UI 为唯一入口，把 Demo 的麦克风、WebRTC、AI 音频、字幕和会话状态拆成模块，接入正式的自由对话页面。随后我完成了 GitHub 管理、生产网关、Vercel 部署、域名、安全检查和真实链路验收。

### 0:40—1:30：为什么不能直接部署本地版本

本地链路是 React 连接 Python aiohttp，再由 Python 连接阿里云百炼。它本地可用，但原后端依赖进程内状态和本地文件，不能假设 Vercel Serverless 的实例持续存在，也不能把本地文件系统当成生产存储。

因此真正的问题不是“怎样点击部署”，而是怎样把本地架构改成适合云端的结构，同时保留已经跑通的实时能力。

### 1:30—2:30：我的生产架构选择

我采用“Vercel 前端、Supabase Edge Function 控制面、百炼 WebRTC 媒体面”。Vercel 托管 React 页面；Edge Function 校验来源、创建会话、交换 SDP、保存最终字幕和质量指标；持续音频则由浏览器和百炼通过 WebRTC 传输，不经过数据库，也不由 Edge Function 长时间中转。

这样设计可以复用原有 Vercel、Supabase、数据库和域名，不增加新的云平台；Edge Function 适合处理短请求；百炼密钥也能始终留在服务端。

### 2:30—3:35：我是怎么实施的

前端被拆成会话 Hook、实时客户端、麦克风、AI 播放器、状态 reducer 和 API 客户端。页面只负责 UI 和统一状态，避免 WebRTC 事件散落在组件里。一次通话只创建一个麦克风流、PeerConnection、DataChannel 和播放器。

服务端我升级了原 Supabase 项目的 `realtime-gateway`，提供 session 创建、SDP、字幕事件、质量上报和关闭接口，并沿用已有数据库表和 RLS，没有新建 Supabase 项目或修改 schema。

部署时先把代码推到 GitHub，再把前端连接到原 Vercel 项目。Vite 只注入公开的网关 URL 和 publishable key；百炼 API Key、service role 和其他 secret 不进入浏览器、日志或 GitHub。

### 3:35—4:25：实时对话如何运行

用户点击开始后，浏览器申请麦克风并创建会话，然后生成 WebRTC Offer SDP。Edge Function 使用服务端百炼密钥交换 Answer SDP。连接建立后，用户和 AI 音频通过 WebRTC 传输，字幕和控制事件通过 DataChannel 返回，再由统一 reducer 映射成页面状态。

结束、断网、异常和页面卸载都进入同一个幂等 teardown，停止麦克风、AudioContext 和动画帧，关闭 DataChannel 与 PeerConnection，并上报质量、关闭数据库会话，避免残留麦克风或重复连接。

### 4:25—5:30：上线中解决的关键问题

第一个问题是 Edge Runtime 读取提示词文件路径不稳定，导致 Worker 500。我先增加失败测试，再把审核后的提示词嵌入函数，同时保留文本作为审计资产。

第二个问题是 Vercel 首次构建没有拿到 Production 环境变量，线上仍回退到 localhost。我增加构建产物检查，确认网关 URL 和公开 key 存在、localhost 回退不存在后才部署。

第三个问题是 `www` 和根域名能打开页面，但点击对话出现 `Failed to fetch`。我先比较三个域名的资源哈希，确认不是旧版；再通过 OPTIONS 预检和 Edge 日志定位到 CORS 403。补充两个精确来源和回归测试后，三个域名预检全部恢复为 204。

### 5:30—6:20：我怎样证明真的上线

我按三层验证。代码层运行 lint、TypeScript 检查、45 项前端测试、后端测试和 production build，并扫描客户端产物是否包含服务端密钥。接口层验证 session 创建、SDP、字幕、质量上报和关闭。用户层通过正式域名检查麦克风、WebRTC、AI 开场音频、实时字幕和结束清理。

线上日志显示 session 创建 201、SDP 交换 200、质量上报成功、session DELETE 200。因此我验证的不是“首页能打开”，而是完整实时调用链。

### 6:20—7:00：总结

这一阶段，我把一个可演示的实时语音 Demo 转化成了有统一产品入口、清晰模块边界、服务端密钥保护、正式域名和故障定位能力的线上系统。

下一阶段重点不是盲目增加功能，而是补齐真实设备矩阵、Preview 自动化、监控告警、成本指标和容量测试，让系统从可上线继续走向可规模化运营。

## 五、项目设计亮点

### 1. UI 和实时能力解耦

页面不知道底层 WebRTC 的每一种事件，只消费统一状态和 actions。这样将来更换模型供应商或调整实时协议时，不需要重写整个 UI。

### 2. 控制面和媒体面分离

Edge Function 处理鉴权、会话和 SDP，实时音频通过 WebRTC 传输。服务端不持续中转音频，降低延迟和网关带宽压力。

### 3. 单一资源所有权

一次通话只允许一个麦克风流、一个 PeerConnection、一个 DataChannel、一个播放器和一个 AudioContext。统一 teardown 保证资源只释放一次。

### 4. 生产密钥边界清晰

公开配置可以进入 Vite bundle；高权限密钥只能出现在服务端。判断标准不是变量是否叫“环境变量”，而是它最终运行在浏览器还是服务端。

### 5. 用可验证证据驱动上线

每个关键故障都有复现证据、最小修复和回归测试。线上验收同时查看浏览器、HTTP 状态、Edge 日志和数据库状态。

## 六、评委可能问的问题与推荐回答

### A. 架构与技术选型

#### 1. 为什么不直接把自由对话 Demo 嵌入完整 UI？

因为 iframe 或双应用跳转只能解决“看起来能进入”的问题，无法解决状态共享、统一路由、视觉一致性和资源释放。我的方案是复用 Demo 的真实链路，但把它拆成麦克风、实时客户端、播放、状态和 API 模块，由完整 UI 作为唯一页面外壳。这使每个模块可以独立测试，也避免重复创建连接。

#### 2. 为什么生产后端选择 Supabase Edge Function？

项目已经使用 Supabase，并且已有数据库、RLS、环境变量和实时相关表。生产网关主要处理短生命周期的会话创建、SDP 交换和事件落库，适合 Edge Function。这样既复用现有资源，又避免新增容器平台和运维面。

#### 3. 为什么不把 Python 后端直接部署到 Vercel Functions？

原 Python 后端依赖进程内状态和本地文件，而 Vercel Functions 是无状态、弹性销毁的运行模型，不能假设请求落在同一个实例。本地写文件也不能作为持久化方案。强行迁移会隐藏一致性问题，所以我把生产逻辑改造成短请求加数据库状态。

#### 4. Edge Function 能承载“实时对话”吗？

Edge Function 不持续中转实时音频，它只负责控制面：创建会话、交换 SDP、保存事件和关闭会话。真正的媒体面是浏览器与百炼之间的 WebRTC。因此 Edge Function 的无状态特性不会直接限制持续音频传输。

#### 5. 为什么使用 WebRTC，而不是普通 WebSocket？

实时语音更关注低延迟、抖动处理、音轨管理和网络适应。WebRTC 原生支持这些实时媒体能力。DataChannel 还能承载字幕和控制事件。WebSocket 更适合通用双向消息，但如果用它传音频，还需要自己处理更多媒体问题。

#### 6. Supabase 在这个系统里究竟承担什么职责？

它承担两个职责：Edge Function 作为安全会话网关；Postgres 保存学习等级、会话元数据、最终字幕和质量指标。它不是实时模型本身，真正生成语音和文本的是阿里云百炼 Qwen Realtime。

### B. 安全与数据

#### 7. Supabase publishable key 放在前端安全吗？

publishable key 本身就是浏览器公开配置，它的安全性依赖后端权限、RLS 和接口校验，而不是依赖隐藏。真正不能进入前端的是 service role、secret key 和百炼 API Key。我的构建扫描会明确检查这些服务端秘密没有进入客户端产物。

#### 8. 为什么 `verify_jwt=false`，这是不是关闭了安全验证？

不是完全关闭验证，而是不使用 Supabase 用户 JWT 作为入口条件。自由对话当前不要求用户登录，函数内部会校验 publishable key、Origin、频率、请求大小和 session ID。高权限数据库操作只在服务端完成。如果未来接入账号体系，可以再增加 JWT 用户身份和按用户限流。

#### 9. 只校验 Origin 能防住恶意请求吗？

不能，所以系统不是只依赖 Origin。Origin 主要解决浏览器来源约束，同时还会校验 publishable key、请求频率、输入大小和会话有效性。进一步生产化还应增加用户身份、设备信誉、WAF、全局配额和异常成本告警。

#### 10. 用户语音和字幕会被保存吗？

当前不保存原始音频，只保存最终字幕、会话状态和必要的网络质量指标。这样既支持学习记录和故障诊断，也降低隐私和存储压力。后续如果要保存音频，必须增加明确授权、保留期限、删除机制和隐私协议。

#### 11. service role 会绕过 RLS，是否有风险？

有风险，所以 service role 必须只留在服务端，并且不能让客户端自由指定数据库操作。当前所有数据库访问都经过固定的网关路由、字段限制和 session 校验。RLS继续保护公开或浏览器侧访问，但服务端仍需要实施最小权限和严格输入验证。

### C. 部署与运维

#### 12. GitHub、Vercel 和 Supabase 三者分别是什么关系？

GitHub 是代码和变更历史的唯一来源；Vercel负责构建并托管 React 前端；Supabase承载实时网关和数据库。阿里云百炼提供模型能力。它们职责清晰，不把所有能力堆在一个平台里。

#### 13. 为什么复用旧 Vercel 项目，而不是删除后重新建？

旧页面内容可以替换，但项目本身承载域名、环境变量和团队配置。删除项目会无意义地增加 DNS、证书和密钥重配风险。因此我保留项目身份，替换 Production deployment，并清理失效的旧 deployment。

#### 14. 如何确保部署的不是带 localhost 配置的错误版本？

我先执行 Production 预构建，再对构建产物做脱敏布尔断言：必须包含 Supabase Function URL，必须包含现代 publishable key 格式，并且不能包含 localhost 默认地址。三个条件通过后才部署预构建产物。

#### 15. 如果新版本上线失败，怎样回滚？

前端可以将 Vercel Production alias 指回上一条 READY deployment；Edge Function 可以重新部署上一版已验证源码；数据库变化必须通过可逆 migration 管理。本次没有修改 schema，因此回滚面主要是静态前端和 Edge Function，风险相对可控。

#### 16. 为什么三个域名都保留？会不会增加维护成本？

三个域名当前指向同一项目和同一构建，不是三套系统。主入口是 `app`，另外两个保证历史访问和品牌入口可达。为了降低长期维护和统计重复，后续可以把根域名和 `www` 统一 301 跳转到 `app`，并设置 canonical 地址。

### D. 实时链路与可靠性

#### 17. 如何防止用户多次点击后创建多个麦克风和连接？

客户端对 start 做去重，并让 Hook 持有唯一实时客户端。一次会话只有一个麦克风流、一个 PeerConnection 和一个播放器。结束流程是幂等的，即使断线、卸载和用户点击结束同时发生，也只会释放一次资源。

#### 18. 网络断开时系统怎样处理？

PeerConnection 的 failed、disconnected 和 closed 状态会映射到统一会话状态，客户端执行清理并显示重试入口。质量指标会记录丢包、RTT 和 jitter。当前支持显式重试，后续可以根据断线原因增加指数退避自动重连。

#### 19. 字幕为什么既自动滚动，又允许用户手动上滚？

实时对话需要用户持续看到最新字幕，但用户也可能需要回看上一句话。因此只有在滚动位置接近底部时才自动跟随；用户向上滚动后暂停自动跟随，重新回到底部附近时恢复。它比每次强制滚到底部更符合实际阅读行为。

#### 20. 如何证明结束通话后资源真的释放了？

一方面有单元测试验证麦克风轨道、播放器和连接只关闭一次；另一方面线上验收检查结束后质量上报成功、session DELETE 成功、数据库状态变为 closed，并确认页面不保留活动会话。

### E. 测试、故障与工程方法

#### 21. 你是如何定位 `Failed to fetch` 的？

我没有直接判断是 DNS 或旧版本，而是先比较三个域名加载的 JS 资源文件和哈希，确认前端完全相同。然后模拟浏览器 OPTIONS 预检，发现 `app` 返回 204，而 `www` 和根域名返回 403。最后用 Supabase Edge 日志确认拒绝来自 CORS 白名单。修复后重新验证三域名预检、session 创建和 SDP 交换。

#### 22. 为什么构建成功还不算部署成功？

构建工具只能证明代码可以生成产物，不能证明产物包含正确的生产配置，也不能证明外部服务和浏览器权限正常。因此必须继续做构建产物扫描、HTTP 验证、浏览器验证和服务端日志核对。

#### 23. 目前测试覆盖了哪些关键风险？

测试覆盖单一麦克风和播放器所有权、会话 start 去重、资源 teardown、状态映射、实时字幕 reducer、字幕自动跟随、公开 key 请求头、API 路由、提示词一致性、三个正式域名 CORS 契约以及产品页面没有嵌入旧 Demo。

#### 24. 当前还有哪些没有完全验证？

真人在不同设备和浏览器上长时间说话时的转写准确率、弱网下的自动重连、大并发容量和长期成本还需要更系统的验证。现阶段已经验证了麦克风权限、会话建立、WebRTC、AI 音频、AI 字幕和资源清理，但我不会把尚未完成的容量测试说成已完成。

### F. 产品价值与下一步

#### 25. 这次工作对产品价值最大的提升是什么？

它把“技术 Demo”变成了“用户可以通过正式产品入口使用的真实功能”。同时建立了模块边界、密钥安全、线上诊断和可重复部署流程，后续开发场景训练、用户系统和学习报告时不需要推翻实时底座。

#### 26. 如果用户量扩大十倍，最先可能遇到什么问题？

首先关注模型并发和调用成本，其次是会话创建限流、Edge 冷启动、数据库写入量和弱网体验。解决方向包括按用户配额、全局限流、队列化非关键指标、监控 P95 建连时间、模型成本看板和容量压测。

#### 27. 下一阶段最优先做什么？

我会优先做三件事：建立 Preview 自动部署和回归验收；增加错误率、建连时间和成本监控；完成 Chrome、Safari、iOS 和 Android 的真实设备测试。它们比继续增加页面功能更能降低真实用户使用风险。

#### 28. 这套架构是否被阿里云百炼绑定？

当前实时协议适配层依赖百炼，但 UI、麦克风、播放器和状态管理已经与供应商事件隔离。未来如果更换模型，主要修改实时客户端协议适配和服务端网关，不需要重写产品页面。这也是模块化融合的价值。

## 七、评委追问时的回答方法

建议每个回答使用三步：

1. 先给结论，例如“没有把音频持续经过 Edge Function”；
2. 再给一个技术原因，例如“媒体面使用 WebRTC，Edge 只负责控制面”；
3. 最后给证据或边界，例如“线上 SDP 返回 200，但大并发仍需要压测”。

不要只回答工具名称，也不要把尚未验证的能力说成已经完成。评委更关注的是：你是否理解选择背后的约束，是否知道系统当前的边界，以及是否能用证据证明结果。
